S-03 · Đăng nhập  (Login Screen)
Route: /login
Quyền truy cập: Khách
1. Mô tả (Description)
Màn hình xác thực người dùng đã có tài khoản. Hỗ trợ 3 phương thức: Google OAuth 2.0, Email + mật khẩu, và Email OTP (không mật khẩu). Sau khi xác thực thành công, hệ thống cấp Access Token (RAM) + Refresh Token (Cookie HttpOnly) và điều hướng người dùng theo trạng thái tài khoản (chưa onboarding / chưa chẩn đoán / sẵn sàng).
Đây là màn hình chịu tải bảo mật cao: áp rate limit, khoá tạm khi sai nhiều, và ghi nhật ký bảo mật cho mọi lần đăng nhập.
2. Điểm vào (Entry points)
Từ Landing (menu 'Đăng nhập').
Từ màn Đăng ký (link 'Đã có tài khoản?').
Bị điều hướng về khi truy cập trang cần đăng nhập mà chưa xác thực.
Từ email/liên kết khôi phục.

7. Business logic (quy tắc màn hình)
Sai thông tin → thông báo TRUNG TÍNH 'Email hoặc mật khẩu không đúng' (không tiết lộ email có tồn tại hay không).
Sai > 5 lần trong cửa sổ thời gian → hiện CAPTCHA và tạm khoá 15 phút theo IP/email; ghi SecurityAuditLog.
Tài khoản isSuspended → chặn đăng nhập, hiển thị hướng dẫn liên hệ hỗ trợ.
Điều hướng sau đăng nhập theo cờ: needsOnboarding→S-05, needsDiagnostic→S-06, ready→S-10.
Chống double-submit: disable nút khi đang gửi.
Chỉ 01 phiên thi tích cực: nếu có attempt đang dở, xử lý theo quy tắc 'chuyển phiên'.

B. Luồng Nghiệp vụ / Logic (Business Logic Flows)
B.1. Xác thực & phiên (Authentication)
login(email, password):
  user = findByNormalizedEmail(email)
  if !user or !verifyArgon2(password, user.hash):
      audit(LOGIN_FAIL); incFailCounter(); 
      if fails > 5: requireCaptcha(); lock(15m)
      return 401 AUTH_INVALID_CREDENTIALS
  if user.isSuspended: return 403 AUTH_ACCOUNT_SUSPENDED
  access = signJWT(user, 15m)
  refresh = issueRefreshToken(user)          // lưu hash vào Session
  audit(LOGIN_OK)
  return { access, nextStep: resolveNextStep(user) }
 
refresh(token):                              // Refresh Token Rotation
  s = findSessionByHash(hash(token))
  if !s or s.isRevoked: return 401
  if s.rotatedAlreadyUsed: revokeAllSessions(user); audit(TOKEN_REUSE); return 401
  rotate(s); return newAccess
Quy tắc chính
Access 15' (RAM), Refresh 7 ngày (Cookie HttpOnly/Secure/SameSite=Strict).
OTP 6 số TTL 5', ≤5 sai → khoá 15'.
Chỉ 01 phiên thi tích cực.

B.3. Vòng đời lượt thi & chấm điểm
submit(attemptId, answers):
  if attempt.status == COMPLETED: return cachedResult   // idempotent
  rawLC, rawRC = grade(answers)
  scaledLC = ScoreConversion(rawLC, LISTENING, examId)
  scaledRC = ScoreConversion(rawRC, READING, examId)
  total = clamp(scaledLC + scaledRC, 10, 990)
  if mode==FULL_TEST and elapsed < 600s: status = FLAGGED_REVIEW
  else: status = COMPLETED
  hash = HMAC_SHA256(attemptId|userId|scaledLC|scaledRC|submittedAt, SECRET)
  pushWrongToNotebook(); updateMastery(); delta = total - lastSameExam
  if status==COMPLETED: grantGems(EXAM_COMPLETE, refId=attemptId)   // idempotent
  return result
Quy tắc chính
Nộp idempotent theo attemptId.
Δt<600s (full-test) → FLAGGED, không tự loại.
Không lộ đáp án khi đang thi.

B.6. Kinh tế Gems (ledger idempotent)
grantGems(reason, refId, amount):
  // @@unique(userId, reason, refId) chặn cấp trùng
  if exists(userId, reason, refId): return   // đã cấp
  insert GemTransaction(+amount); journey.currentGems += amount
 
spendGems(itemPrice, purchaseRequestId):
  if currentGems < itemPrice: return 402 INSUFFICIENT_GEMS
  if itemLimitReached: return 409 ITEM_LIMIT_REACHED
  insert GemTransaction(-itemPrice, SHOP_SPEND, purchaseRequestId)  // idempotent
Quy tắc chính
Nguồn: EXAM_COMPLETE +50, TARGET_HIT +100, DAILY_LOGIN +5 (mốc +20), QUEST_* +10..50.
Tiêu: Khiên 100 (trần 3).

C. Luồng Tích hợp Hệ thống (Integration System Flows)
C.1. Google OAuth 2.0
1. Client bấm 'Tiếp tục với Google' → GET /auth/oauth/google/start (server tạo state, PKCE).
2. Redirect tới Google consent → người dùng đồng ý.
3. Google callback → GET /auth/oauth/google/callback?code&state (server verify state).
4. Server đổi code lấy token, lấy hồ sơ (email verified).
5. Tìm/tạo User theo normalizedEmail (liên kết nếu đã tồn tại) → cấp Access+Refresh → điều hướng.
C.2. Email OTP (nhà cung cấp email)
1. POST /auth/otp/request → server sinh OTP 6 số, lưu Redis TTL 5', rate limit.
2. Gọi Email Provider (SMTP/API) gửi OTP; ghi log gửi.
3. POST /auth/otp/verify → so khớp Redis; đúng → xoá OTP, cấp token.
4. Sai/hết hạn → mã lỗi tương ứng; ≤5 lần sai → khoá.
C.3. Media âm thanh (S3 signed URL)
1. Client cần audio đề → server cấp signed URL (TTL ngắn) từ S3.
2. Client stream trực tiếp từ S3/CDN (payload câu hỏi KHÔNG kèm audioScript/đáp án).
3. URL hết hạn nhanh để hạn chế chia sẻ; không phải cơ chế chống trích xuất tuyệt đối.
C.4. Thanh toán (Payment Provider + Webhook)
1. S-24: POST /subscription/checkout → server tạo phiên checkout ở provider → trả checkoutUrl.
2. Client redirect tới provider, hoàn tất thanh toán.
3. Provider gọi Webhook về server (ký số) → server verify chữ ký.
4. Cập nhật Subscription(status, currentPeriodEnd); KHÔNG tin trạng thái từ client.
5. Client quay lại app → GET /subscription/status phản ánh kết quả.
✔ Thao tác thanh toán/khởi tạo do người dùng chủ động; hệ thống chỉ tạo phiên & xác nhận qua webhook có chữ ký.
C.5. Thông báo đẩy / Email nhắc học
1. Job nền phát hiện điều kiện (streak sắp đứt, quest mới, mở khoá) → tạo Notification.
2. Nếu người dùng bật push/email → đẩy qua provider tương ứng (tôn trọng tuỳ chọn & giờ nhắc).
3. Client GET /notifications hiển thị; đánh dấu đã đọc.
